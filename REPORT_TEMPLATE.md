# Report generation spec

Instructions for turning `model_output.json` into the published HTML
artifact ("Home Buying Financing Plan"). Follow this structure exactly
regardless of what inputs produced the JSON — the report's sections, order,
and table shapes are fixed; only the numbers and narrative sentences change.

## Pipeline

1. Edit `home_model_config.yaml` (or answer the interactive prompts) with
   your own deal and income inputs.
2. Run `python3 home_model.py`. This writes `model_output.json` — no HTML
   is generated by the script.
3. Hand `model_output.json` to Claude with this file and ask it to publish
   the report as an Artifact. Use the primary scenario (first entry in
   `scenarios[]`, or whichever one the user names) as the report's subject;
   other scenarios in the file are supporting comparisons, not separate
   reports.

## Required sections, in order

1. **Header** — property/deal name (ask the user if not inferable),
   headline `<h1>`, table of contents, and a "Scenarios" box summarizing:
   purchase price, down payment + LTV% + rate, mortgage structure, rent
   baseline. Pull LTV/rate from `affordability.ltv` and `params.interest_rate`.

2. **Bottom line** (`.verdict` box) — 2-4 sentences of synthesis: is the
   down payment amount justified (see down-payment-scenarios section
   below), what's the affordability trajectory, what's the main residual
   risk. Write this from the computed numbers; do not invent facts.

3. **Monthly cost & affordability** — four stat cards from `affordability`:
   net monthly cost (`total_own_gross`), share of income today
   (`total_own_pct_net`, labeled with `verdict`), share after any secondary
   income change if `verdict_after_ruling` is non-null, and the stress-test
   share (`stress_pct_net`). Color ideal=green, acceptable=orange,
   stretched=orange/red, exceeds=red — match `verdict_color`.

4. **Cost of owning vs. cost of renting, by market scenario** — one table
   row per entry in `appreciation_results`, one column per hold-year
   snapshot (from `hold_years_grid`), values from each snapshot's
   `vs_rent_if_sold`. Include each scenario's `breakeven_year` as a badge
   under its name (or "never" if null).

5. **Would you owe money if you had to sell?** — same row/column shape,
   values from each snapshot's `equity_net_of_selling_costs` directly —
   it's already net of both selling costs and remaining mortgage balance.

6. **Down payment amount comparison** — from `down_payment_scenarios.rows`.
   Show the base/current contribution, the `is_optimal` row, and 2-3
   bracketing rows (smaller and larger) for contrast — not all ~140 rows.
   Mark the optimal row with "(peak)"; the peak's own `net_benefit` reads
   as 0.

7. **Methodology & assumptions** — a const-grid of the key rate/tax
   assumptions read straight from `params`: interest rate, mortgage
   structure, mortgage interest deduction rate, eigenwoningforfait rate,
   OZB rate, Box 3 deemed returns and tax rate, rent baseline and growth,
   selling costs, capital gains rate, idle cash return, affordability
   bands, stress-test bump.

8. **Open items** — freeform list of caveats worth naming: rate-tier
   reclassification thresholds, mortgage structure tradeoff (annuity vs.
   linear, if not obviously settled), WOZ-vs-offer-price approximation,
   rent-growth assumption vs. legal cap. Adapt to what's actually notable
   given the inputs — don't copy stale caveats from a prior run if they no
   longer apply.

9. **Footer** — one line: `Model: home_model.py`, plus a note on what
   calibrated the appreciation scenarios (ask the user, or omit if none).

Note: the report intentionally excludes a net-worth balance sheet and a
down-payment funding-source breakdown — those require inputs the model
doesn't collect (full account-level net worth) and were dropped to keep
the input surface minimal.

## Style

Match the existing artifact's visual system: serif display headings
("Fraunces"), mono numerals/labels ("IBM Plex Mono"), sans body text ("IBM
Plex Sans"), a light/dark CSS-variable theme, `.finance-cards` stat grid,
`.const-grid` for assumptions, `.tablewrap` bordered tables with
good/bad color classes on numeric deltas. Reuse the CSS from the last
published version rather than redesigning it each run — the format is
meant to stay stable across inputs.
